# 《未来战争》Agent 实现计划

## 1. 项目目标

实现一个可长期运行、可调试、可扩展的《未来战争》参赛 Agent。

Agent 需要完成以下工作：

```text
正确解析判题器 Request
根据当前状态生成 Response
白天运行两个工人的固定流水线
白天运行开拓者自进化任务 Agent
夜晚根据 targetTeam 防守我方基地
我方机器人清空后恢复白天流水线
利用任务、经济、升级和宝藏获得额外收益
避免非法指令和重复失败
```

最终目标不是把所有逻辑写在一起，而是形成一套可以逐步增强的 Agent 框架：

```text
协议层稳定
状态层清晰
角色逻辑独立
策略参数可配置
动作统一校验
跨回合记忆可靠
测试可以回放
```

## 2. 总体实现路线

项目分为五个阶段：

```text
阶段一：协议层和基础框架
阶段二：两个工人固定流水线
阶段三：夜晚战斗和回防
阶段四：开拓者自进化 Agent
阶段五：经济、宝藏和策略优化
```

每个阶段都必须做到：

1. 代码可以启动。
2. Request 可以被解析。
3. Response 格式合法。
4. 旧功能不被新功能破坏。
5. 有对应的单元测试或 Request 回放测试。

不要等所有功能完成后才测试。每个阶段都要有一个可运行版本。

## 3. 可维护性设计原则

### 3.1 不把策略写死在 HTTP 层

`server.py` 只负责：

```text
接收 HTTP 请求
解析 JSON
调用 planner
序列化 Response
处理最外层异常
```

它不应该包含：

```text
工人怎么挖矿
武器怎么攻击
任务怎么回答
墙怎么建设
```

### 3.2 不把所有逻辑写在 brain.py

当前 `brain.py` 适合 Demo，但正式实现后要拆分：

```text
protocol.py  -> 数据结构和 Request/Response 解析
memory.py    -> 跨回合记忆
planner.py   -> 总调度
workers.py   -> 工人 1/工人 2 状态机
pioneer.py   -> 开拓者任务 Agent
combat.py    -> 夜晚防守和武器目标
economy.py   -> 采矿、卖矿、购买、升级
layout.py    -> 基地、主攻面、武器、墙目标
commands.py  -> 动作构造和合法性校验
grid.py      -> 寻路
```

模块之间只通过明确的数据结构和函数接口交互。

### 3.3 规则和参数分离

容易变化的内容不要散落在业务逻辑里：

```python
class StrategyConfig:
    stone_batch_size = 6
    upper_wall_ratio = 0.5
    lower_wall_ratio = 0.5
    return_safety_margin = 5
    task_count_target = 6
    rocket_first = True
```

建议单独放在：

```text
config.py
```

以后修改“每批采多少石头”“侧墙建多少”“升级券顺序”时，只修改配置或队列，不修改多个模块。

### 3.4 使用状态机，不使用大量布尔变量

不要写成：

```python
if has_tower and not has_wall and not is_mining and ...
```

建议使用明确状态：

```text
W1_BUILD_ROCKET
W1_BUILD_RAILGUN
W1_BUILD_GATLING
W1_COLLECT_FRONT_STONE
W1_BUILD_FRONT_WALL
W1_BUILD_UPPER_WALL
W1_BUILD_LOWER_WALL
W1_EARN_MINING
```

状态转换集中写在一个函数中，后期修改流程时只改状态转换，不影响命令构造和寻路。

### 3.5 统一命令出口

所有角色策略只产生“意图”，例如：

```python
Intent(
    role_id=10010,
    action="collect",
    target=stone_mine,
)
```

最终由 `commands.py` 转成接口 JSON。

这样可以集中处理：

```text
字段格式
targetPos 数组
角色类型权限
昼夜限制
距离限制
重复动作
controllerId 冲突
```

## 4. 阶段一：协议层和基础框架

### 4.1 扩展数据模型

当前协议层只解析了部分字段，需要补齐：

```text
TeamOur.type
TeamOur.playerTasks
TeamEnemy.roles
RobotRole.targetTeam
phaseTask
lastRoundRoleActionResults
lastSummonTreasureResult
llmResp
worldNews
lastCmdResult
vendorShopList
weaponShopList
errors
```

建议新增数据类型：

```python
Pos
Zone
Unit
Robot
PlayerTask
WorldNews
GameError
GameState
```

所有外部 JSON 解析集中在 `protocol.py`，角色逻辑不直接读取原始字典。

### 4.2 标准 Response

无论有没有动作，都返回：

```json
{
  "roleCommandMap": {},
  "prompt": "",
  "executeCmd": ""
}
```

内部使用整数 ID，输出时转换为字符串 key。

### 4.3 基础验证

阶段一完成标准：

```text
docs/request.txt 能被完整解析
返回 JSON 可以被 json.loads 解析
所有角色 ID 保留
targetTeam 可以读取
playerTasks 可以读取
shop 列表可以读取
python3 -m compileall 通过
```

## 5. 阶段二：两个工人固定流水线

### 5.1 工人 1

固定流程：

```text
建 rocket
-> 建 railgun
-> 建 gatling
-> 采 stone_batch
-> 建主攻面正面墙，直到本批 stone 用完
-> 重复采 stone / 建正面墙
-> 上侧墙建设到50%
-> 下侧墙建设到50%
-> 进入采矿卖矿
```

批量公式：

```python
batch = min(
    config.stone_batch_size,
    current_wall_stage_remaining,
)
```

默认：

```text
stone_batch_size = 6
upper_wall_ratio = 0.5
lower_wall_ratio = 0.5
```

工人 1 不负责墙体受击后的维修。当前版本只负责初始防线建设。

### 5.2 工人 2

固定流程：

```text
选择一个矿
-> 持续采集该矿
-> 矿点采完或达到批次结束条件
-> 去 vendor
-> 一次性卖掉本轮矿物
-> 检查升级队列
-> 金币够则去 weaponShop
-> 买升级券
-> 到目标建筑周围一格 use
-> 继续下一个矿
```

工人 2 不因为工人 1 的建设状态改变职责。

### 5.3 升级队列配置化

升级队列不要写成多处分散的 `if`，建议使用数据表：

```python
UPGRADE_QUEUE = (
    UpgradeGoal("WeaponUpgradeVoucher1", "rocket", 1, 2),
    UpgradeGoal("StationUpgradeVoucher1", "station", 1, 2),
    UpgradeGoal("WeaponUpgradeVoucher2", "rocket", 2, 3),
    UpgradeGoal("WeaponUpgradeVoucher1", "railgun", 1, 2),
    UpgradeGoal("WallUpgradeVoucher1", "front_wall", 1, 2),
    UpgradeGoal("StationUpgradeVoucher2", "station", 2, 3),
    UpgradeGoal("WeaponUpgradeVoucher2", "railgun", 2, 3),
    UpgradeGoal("WallUpgradeVoucher2", "front_wall", 2, 3),
)
```

升级选择器只负责：

```text
找到第一个满足条件的升级目标
检查金币
检查商品存在
检查目标建筑存在
返回购买意图
```

这样以后调整购买顺序只改队列表。

## 6. 阶段三：夜晚战斗和回防

### 6.1 机器人筛选

优先按接口字段：

```python
our_robots = [
    robot for robot in state.robots
    if robot.target_team == state.team_type
]
```

场上可能同时有两拨机器人：

```text
targetTeam == 我方 -> 我方防守目标
targetTeam == 敌方 -> 默认不占用我方角色
```

没有 `targetTeam` 时，使用基地位置和主攻面推断，无法判断则保守防守。

### 6.2 基地和主攻面

```text
左上基地：
    机器人从右上出生
    主攻面是基地右侧

右下基地：
    机器人从左下出生
    主攻面是基地左侧
```

布局模块只输出目标集合：

```text
tower_targets
front_wall_targets
upper_wall_targets
lower_wall_targets
```

不把坐标硬编码在工人状态机里。

### 6.3 夜晚两种模式

```text
our_robots 非空：
    三人全部回防
    回到武器旁
    控制三座武器

our_robots 为空：
    机器人波次结束
    工人恢复各自流水线
    开拓者恢复任务/宝藏/辅助流程
```

这两个模式必须是显式状态，不要在每个角色模块里各自判断，避免三个人出现不一致。

### 6.4 回防阈值

```python
required = path_length(role.pos, role_night_stand)
if rounds_to_night <= required + config.return_safety_margin:
    role_mode = RETURN_DEFENSE
```

进入回防模式后，角色不能继续采矿、交易或任务移动。

## 7. 阶段四：开拓者自进化 Agent

这是整个项目最重要的高收益部分。

### 7.1 六任务目标

在累计完成 6 个自进化任务前：

```text
开拓者优先接取和完成任务
```

完成 6 个任务后：

```text
开拓者转为购买/升级/宝藏辅助角色
```

任务点是否可接由接口判断：

```text
isValid == true
coldDownRounds == 0
```

### 7.2 Agent 闭环

```text
移动到己方任务点周围一格
-> acceptTask
-> 读取 phaseTask
-> 判断是否已有 SOP
-> 没有 SOP：executeCmd 探索
-> 读取 lastCmdResult
-> prompt 总结规则
-> 保存 SOP/SKILL
-> 生成答案
-> submitAnswer
```

后续同类任务：

```text
识别任务族
-> 读取 SOP
-> 替换本次输入
-> 执行必要命令
-> 校验结果
-> submitAnswer
```

### 7.3 SOP 设计

SOP 必须存通用规则，不存一次性答案：

```python
class SOP:
    task_family: str
    input_fields: tuple[str, ...]
    command_templates: tuple[str, ...]
    output_schema: str
    answer_template: str
    validation_rules: tuple[str, ...]
    version: int
```

### 7.4 任务答案管理

维护：

```text
当前答案
历史答案
历史最高通过率
错误字段
任务剩余回合
```

任务超时按此前最高通过率结算，因此：

```text
不要用低通过率答案覆盖历史最佳答案
接近超时时提交历史最佳答案
```

### 7.5 任务能力可替换

任务求解器不要写死在 `pioneer.py`：

```text
TaskRecognizer
TaskExplorer
SOPBuilder
AnswerGenerator
AnswerValidator
```

未来增加新的任务类型时，只新增一个识别器或求解器，不修改总调度流程。

## 8. 阶段五：经济、宝藏和优化

### 8.1 经济

经济模块负责：

```text
根据 vendorShopList 选择矿物
批量卖矿
根据升级队列检查购买目标
在 weaponShop 周围一格 buy
将升级券送到目标建筑旁 use
```

工人 1 墙完成后接入相同的赚钱模块，不复制一套新逻辑。

### 8.2 宝藏

宝藏模块独立维护：

```text
folkLegends 历史
宝藏位置假设
开启时间假设
祭品假设
lastSummonTreasureResult
```

只有高置信度时才执行 `summonTreasure`，因为合法动作也会消耗祭品。

### 8.3 战斗优化

初版先保证合法和稳定：

```text
gatling：单目标
railgun：单目标
rocket：单落点
```

后续再增加：

```text
rocket 3 x 3 最优落点
railgun 穿透估值
gatling 90 度多目标分组
```

不要让高级优化影响基础防守稳定性。

## 9. 状态和记忆设计

### 9.1 单回合状态

单回合状态来自当前 Request，不写回业务对象：

```text
GameState
```

### 9.2 跨回合状态

跨回合状态写入：

```text
PersistentMemory
```

包括：

```text
工人流水线阶段
当前矿点
当前采集批次
当前任务
SOP
历史最佳答案
失败动作
新闻历史
宝藏推断
```

### 9.3 状态恢复

如果进程重启：

1. 读取本地 memory 文件。
2. 根据新 Request 校准角色实际位置和背包。
3. 如果记忆与当前状态冲突，以当前 Request 为准。
4. 清理已经完成或失效的目标。

### 10.1 测试分层

```text
单元测试：
    坐标、距离、基地 footprint、目标选择、命令校验

状态机测试：
    工人1、工人2、开拓者各状态转换

```

### 10.2 必测场景

1. 初始 75 金币，三塔建设顺序正确。
2. 工人 1 每批最多采 6 个 stone。
3. 正面墙优先，上下墙各完成约 50%。
4. 工人 2 一个矿采完后再卖。
5. 升级券按队列购买，围墙券可穿插。

9. 后续任务能复用 SOP。
10. 任务超时能保留最高通过率答案。
11. 6 个任务完成后开拓者切换角色。
12. 所有动作不违反角色、昼夜和距离限制。

## 13. 后期修改方式

以后常见调整对应的修改位置：

| 需求变化 | 修改位置 |
| --- | --- |
| stone 每批数量变化 | `StrategyConfig.stone_batch_size` |
| 上下侧墙比例变化 | `upper_wall_ratio` / `lower_wall_ratio` |
| 升级购买顺序变化 | `UPGRADE_QUEUE` |
| 武器建造顺序变化 | `TOWER_BUILD_ORDER` |
| 角色固定职责变化 | `roles.py` / 对应状态机 |
| 夜晚回防提前量变化 | `return_safety_margin` |
| 新增任务类型 | `TaskRecognizer` / 对应 Solver |
| SOP 格式变化 | `SOP` 数据结构和序列化 |
| 新增商店商品 | `economy.py` 商品规则 |
| 新增武器攻击策略 | `combat.py` 目标选择器 |
| 新增布局方式 | `layout.py` |

不要为了一个参数变化去修改 `server.py`、协议解析或所有角色模块。

## 14. 最终实现思路

### 14.1 第一版代码已落地的模块

当前可运行骨架已经落在 `Demo/CoreGeek/src/agent` 下：

```text
brain.py       -> 兼容入口，只负责调用 Planner
planner.py     -> 昼夜和全局防守/运营调度
protocol.py    -> Request 数据模型和 targetTeam/任务/商店解析
memory.py      -> 跨回合流水线和任务 Agent 记忆
workers.py     -> 工人1、工人2固定职责
pioneer.py     -> 自进化任务的探索/执行/作答阶段
combat.py      -> 我方机器人筛选、回防和控炮
economy.py     -> 卖矿、买升级、升级目标
layout.py      -> 基地角落、主攻面、武器和墙目标
commands.py    -> 动作构造和响应前校验
```

当前实现已经覆盖：

1. 左上/右下基地识别，以及右侧/左侧主攻面布局。
2. 工人1“火箭->电磁炮->加特林->主攻面墙->上下侧墙半量->赚钱”。
3. 工人2“采完整个矿->卖矿->去武器商店->按升级队列购买->使用升级券”。
4. `targetTeam` 筛选，只有攻击我方的机器人触发全员夜间防守。
5. 我方机器人清空后的夜间运营恢复。
6. 开拓者任务点移动、任务驻留约束，以及 `prompt/executeCmd/submitAnswer` 的基本 Agent 流程。
7. 矿区、商店、任务点、武器等阻挡物的周围一格寻路。
8. 按角色类型和昼夜阶段过滤非法动作。
9. 结构化 JSONL 日志、日志滚动、异常堆栈和动作过滤原因记录。
10. 工人 1 批量采石状态、工人 2 单矿采完再卖状态。
11. 固定武器绑定、动作失败恢复、多目标炮台攻击。
12. SOP 可选 JSON 持久化和 request 回放校验脚本。

后续扩展优先修改：

```text
采石批次、侧墙比例、回防提前量、升级顺序 -> config.py
墙/武器位置规则                         -> layout.py
工人职责状态                            -> workers.py
任务 Agent 的命令抽取和答案策略          -> pioneer.py
机器人目标选择和武器分配                 -> combat.py
```

这样策略调参不需要修改 HTTP 服务、协议解析和其他角色模块。

### 14.2 日志记录设计

日志目录默认为：

```text
Demo/CoreGeek/logs/agent.log
```

也可以通过环境变量修改：

```text
AGENT_LOG_DIR=/path/to/logs
AGENT_LOG_LEVEL=DEBUG
```

每个决策回合至少记录：

### 14.3 当前还需要优化的重点

按优先级排序：

1. **任务 Agent 持久化 SOP**：把第一次自进化任务得到的探索命令、输出摘要、答案格式保存下来，后续相似任务优先复用。
2. **升级券实际名称和等级映射**：根据判题器真实商品清单校准每张券对应的等级和目标建筑。
3. **矿点采集状态**：已经记录成功 `collect` 次数，并以单矿10次、矿点消失或背包满作为卖矿条件；后续可根据真实回放进一步校准异常刷新规则。
4. **武器控制绑定**：已经固定 `worker1/pioneer/worker2` 与武器的绑定关系，后续继续根据实战调整绑定优先级，避免建筑位置变化导致角色频繁换炮。
5. **多目标攻击**：已经支持火箭/加特林按等级选择多个目标，并对加特林做同向锥形筛选；后续可继续优化伤害收益计算和电磁炮穿透目标。
6. **新闻与宝藏策略**：增加官方消息价格变化解析、民间传闻摘要和祭品校验。
7. **状态异常恢复**：根据 `lastRoundRoleActionResults` 自动重试寻路、重新选择目标，并在连续失败时降级为回基地。
8. **回放测试**：积累白天建造、卖矿、购买升级券、夜晚防守、任务超时和角色死亡等真实 Request 序列。

运行态记忆会在检测到 `roundNo` 回退时自动清理，避免新局继承上一局的失败次数和角色阶段；SOP 知识库会保留，用于后续相似自进化任务复用。

### 14.4 Request 回放

在 `Demo/CoreGeek` 目录执行：

```bash
python3 tests/replay_request.py
```

脚本会读取项目根目录的 `docs/request.txt`，调用完整 Planner，并校验：

```text
顶层响应字段完整
角色 ID 是字符串数字
动作名称属于接口规定集合
需要 targetPos 的动作确实携带坐标
attack 确实携带 controllerId
```

当前已经落地的绑定规则为：

```text
worker1 -> rocket
pioneer  -> railgun
worker2 -> gatling
```

如果目标武器尚未建成，角色会暂时选择当前可用武器；目标武器建成后恢复固定绑定。

动作连续失败达到阈值后，Planner 会进入 `failure_recovery`，让失败角色向其绑定武器或基地移动，避免重复执行同一条卡死动作。

最终程序的主循环保持简单：

```python
def decide(payload):
    state = GameState.from_payload(payload)
    memory = memory_store.load()
    memory.update_from_state(state)

    if state.is_day:
        intents = planner.plan_day(state, memory)
    else:
        intents = planner.plan_night(state, memory)

    response = command_builder.build_response(intents, state, memory)
    memory_store.save(memory)
    return response
```

复杂度被分散到各自模块：

```text
planner    只负责总流程
workers    只负责两个工人
pioneer    只负责任务 Agent
combat     只负责夜晚防守
economy    只负责经济和升级
layout     只负责位置目标
commands   只负责合法输出
memory     只负责跨回合记忆
```

这样做的结果是：策略可以继续变化，但接口层、状态层、角色层和命令层不会互相牵连，后期修改成本可控。
